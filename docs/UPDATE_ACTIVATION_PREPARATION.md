# macOS 应用内更新准备

范围：Apple Silicon、Beta 通道、完整包更新。用户于 2026-09-14 同意落实准备工作。
本文件记录当前实施路径；验证结果以`PROJECT_STATE.md`为准，旧候选证据保留在
`BETA_ACTIVATION_HANDOFF.md`。这不是公开激活或已安装版本可更新的声明。

用户随后于同日明确授权官网部署及云端升级上线。官网已独立部署；应用更新仍受
下述安装保护/验收门槛约束，不再把发布许可本身列为缺项。临时协调进程的具体
架构决策仍待确认，不把上线授权解释为降低安全门槛。

## 客户端检查策略

- 默认不联网；用户在“软件更新”中开启一次自动检查，偏好持续保留。
- 启动延后 30 秒检查，距最近一次尝试不足 5 分钟时延后，避免频繁重启造成请求循环。
  有编译、PDF 导出或模态对话框时暂缓，在后续定时检查中重试准备条件。
- 每个进程的首次检查不再受 24 小时间隔限制；完成一次尝试后，运行期间每天复查。
  手动检查也满足本次启动检查，不再额外弹出一轮。初始化失败同样登记尝试时间。
- 手动检查可立即请求；关闭自动检查会停止计时器。源码/未配置安装包仍不可联网更新。
- 下载与安装分别由用户确认；原有全窗口保存/取消、签名及正式编译保护不改变。

## 发布配置和现有资源

沿用`release/updates/macos-arm64-beta.json`的渠道、HTTPS 地址和公钥，配置只在构建时
嵌入；不从项目目录加载更新器，不新增网站后端、数据库或下载协议。

准备性只读检查应分别核对：GitHub 仓库权限与已发布版本、Vercel 原项目与域名、
实际 appcast 响应，以及本机安装包身份。接口可读不代表实际上传/部署已被授权。
旧签名记录不等于当前钥匙串访问已经重新验证；本轮不访问私钥或触发签名授权。

新候选必须来自包含当前性能/UI修复的冻结源码，不能发布旧 r2 包来代替当前程序。
待安装保护落定后再同步提升应用版本和发布序号、构建运行时和候选包；可用的下一组
候选身份为`2.1.0-beta.3 / 210003`，这只是计划值，未修改当前版本或发布清单。
N+1 测试包必须使用更高且不冲突的序号；不得覆盖旧 GitHub 资产或旧签名文件。

## 待决定：安装全生命周期保护

现有 GUI 在交接前扫描进程，但 GUI 退出后不持有安装锁。固定 Sparkle 2.9.6 的
`InstallerProgressAppController.m`也明确列出只监视首个实例、晚启动实例及其他登录
会话的限制。重复扫描或只在 GUI 中加锁不能建立跨退出的互斥。

建议下一步先验证一个**只在安装期间运行的临时协调进程**：不常驻、不启动系统服务、
不负责下载/验签/替换文件，也不修改 Sparkle SDK。它只保持安装期保护，参与实例在
启动时协调；安装结束退出。协议须覆盖 GUI 和来自同一安装包的 MCP 入口，不能
静默关闭文稿或改变日常多窗口能力。

这仍是待授权、待验证的方案，不是已实现保护。原型必须证明：锁作用于同一安装
位置而非单一用户会话；交接前已有实例被拒绝；GUI退出后新实例不能进入；安装完成
判断与实际安装器生命期绑定；中断不能误放行或永久阻止恢复。仅有 PID 文件或
“启动成功一次”不足以验收。如不能满足，停止并重新决定，不自行扩展为自定义安装器。

## 有界后续顺序

1. 确认临时协调进程方案，先做上述并发/中断的最小原型，再接正式入口。
2. 冻结源码，运行更新专项及仓库最终检查，一次性生成含更新组件的版本 N 和测试用 N+1。
3. 隔离副本验证完整升级、取消/保存、签名拒绝、晚启动实例、安装中断及外部恢复旧可信包。
   保留原文稿；新包启动后核验实际二进制身份，不能用版本标签代替。
4. 通过上述验收后按已收到的发布授权先发布并匿名核验版本化安装包，再部署签名 appcast，最后检查真实 HTTPS
   客户端升级。原项目、渠道、固定公钥和顺序保持不变。
5. 备份并手动安装首个带更新器的版本，之后才具备应用内升级能力。

Windows、差分更新、运行时渠道切换、自动回滚、常驻服务和 GitHub Actions 不在本次
准备范围。Developer ID/公证属于另行授权的正式分发步骤，不冒充本地 ad-hoc 签名。
